# Changelog — randbotd 3.7.0

**Released:** 2026-09-22

## Summary

This minor release implements **CA-11: Distributed Custodian Swarm & Threshold Key Delegation Engine**, introducing decentralized certificate delegation and a resilient **Dual TCP/UDP Transport Architecture** to `randbotd`.

In `randbotd`, CAs can delegate bounded certificate issuance workloads to a distributed swarm of custodian workers without transferring master private keys or relying on trusted third-party escrow. Version 3.7.0 introduces the 4-step escrow-less delegation handshake over UDP gossip, accompanied by a dedicated, framed TCP streaming subsystem designed to exchange large quantum-ready certificates (e.g., NIST ML-DSA-44 $\ge 4.5\text{ KB}$, RSA-4096) that exceed unfragmented UDP datagram limits ($\le 1400$ bytes). The release also incorporates anti-Slowloris defenses, blind local threshold policies, and a strict silent-drop security posture.

## Key Features & Enhancements

### 1. Distributed Custodian Swarm & Threshold Delegation (`CA-11`)
- **Escrow-less 4-Step Delegation State Machine**:
  - `CustodianContract` (Step 1): Worker proposes terms (`target_ca_id`, `max_work_share_pct`, `valid_until`, `rate_limit_per_minute`, `offered_capabilities`) with cryptographic Ed25519 signature.
  - `CustodianDelegationRequest` (Step 2): CA challenges worker with a random 32-byte cryptographic challenge, candidate mock certificate hash, and binding terms.
  - `CACapabilitiesProof` (Step 3): Worker solves challenge, generates mock certificate conforming to offer parameters, stores it, and returns proof with signature over challenge + cert hash.
  - `SwarmActivationConfirmation` (Step 4): CA validates proof and mock certificate, confirms consensus conditions, and activates worker into the custodian swarm.
- **Cryptographically Bound Timeouts**:
  - Worker signs `valid_until: u64` in the contract.
  - Consensus enforces $\text{activated\_at} \le \text{contract.valid\_until}$ cryptographically, avoiding hardcoded protocol ceilings vulnerable to modified clients.
- **Strict Silent Drop Security Policy**:
  - Unsolicited or invalid contracts/proofs directed at non-seeking CAs, exceeding local private work-share ceilings, or failing validation are dropped with zero network response, defeating scanning/probing attacks.

### 2. Dual TCP/UDP Transport Architecture & Hardened Client
- **Lightweight Framed TCP Streaming Subsystem (`src/net/router/tcp/`)**:
  - Reuses the daemon's configured P2P port over TCP (`0.0.0.0:<port>`), complementing the UDP gossip loop.
  - Custom wire framing (`RBd1\x01\x00` magic header, 32-byte cert hash query, 4-byte length prefix) for on-demand quantum-ready certificate retrieval.
- **Resilient Client Defenses**:
  - Connect timeout: 2.5 seconds.
  - Read/transfer idle timeout: 3.0 seconds (hardened against Slowloris attacks).
  - Exponential backoff: 3 retries with intervals $500\text{ms} \rightarrow 1000\text{ms} \rightarrow 2000\text{ms}$.
  - Strict SHA-256 payload integrity validation against the advertised `mock_cert_hash`.

### 3. Blind Policy Variables & Local Configuration
- **Private CA Threshold Policy (`CaCustodianPolicy`)**:
  - CA operators define `max_work_share_pct`, `min_ttl_seconds`, `target_swarm_size`, and `auto_accept` in private local storage (`ca_custodian_policies.json`).
  - Outside nodes have zero visibility into these internal parameters.
- **Public Visibility Flag**:
  - Added `seeking_custodians: bool` (default `false`) to `CaDeclaration`, enabling CAs to signal participation readiness without leaking threshold values.

### 4. Storage Engine & Cleanliness Modularization
- **Custodian Subtables (`custodians.json`, `ca_custodian_policies.json`)**:
  - Integrated into `Database` via `custodian_subtable.rs` with atomic persistence and event logging.
- **Modular Directory Organization**:
  - Subtables organized in `src/storage/db/subtables/` (`ca_subtable.rs`, `cert_subtable.rs`, `offer_subtable.rs`, `purge_subtable.rs`, `rotation_subtable.rs`, `custodian_subtable.rs`).
  - Catalog logic organized in `src/pki/catalog/` (`offer.rs`, `scope.rs`).
  - Fully conforms to the repository cleanliness constraint ($\le 9$ items per directory, $\le 500$ lines per file).

### 5. Unix Domain Socket IPC Endpoints
- **Operator Swarm Control Plane (`CustodianHandler`)**:
  - `PublishCustodianContract`: Worker node operator proposes terms.
  - `ListCustodians`: Query active custodians and delegation quotas for a CA.
  - `SetSeekingCustodians`: Toggle public swarm solicitation flag.
  - `ConfigureCustodianPolicy`: Update blind threshold policies locally.
  - `RemoveCustodian`: Revoke custodian delegation.

## Operator Tutorial: Configuring Blind Custodian Policies & Swarms

Version 3.7.0 allows Certificate Authority operators to recruit and coordinate a decentralized custodian swarm without leaking private operational parameters or threshold ceilings to prospective attackers.

### Step 1: Establish Your CA's Blind Policy (`ConfigureCustodianPolicy`)
A CA's threshold parameters are strictly **blind**: they are persisted locally in `ca_custodian_policies.json` and are never broadcast over the network. Any worker petition violating these local bounds is dropped silently with zero response.

To configure your CA's blind policy via the IPC socket:
```json
{
  "ConfigureCustodianPolicy": {
    "ca_id_hex": "<CA_ID_HEX>",
    "max_work_share_pct": 25,
    "min_ttl_seconds": 3600,
    "target_swarm_size": 10,
    "auto_accept": true
  }
}
```
**Parameter Reference**:
- `max_work_share_pct` (e.g., `25`): Maximum workload percentage any single worker may claim. Petitions asking for more than this ceiling are silently ignored.
- `min_ttl_seconds` (e.g., `3600`): Minimum contract validity period (in seconds). Prevents excessive churn from ephemeral nodes.
- `target_swarm_size` (e.g., `10`): Maximum active worker count for this CA. Petitions arriving when the swarm is at capacity are silently dropped.
- `auto_accept` (`true` / `false`):
  - `true`: Compliant candidate petitions are automatically challenged, verified over TCP, and activated into the swarm.
  - `false`: Candidate petitions are staged in `pending_contracts` for operator manual review.

### Step 2: Signal Solicitation Readiness (`SetSeekingCustodians`)
By default, all CAs have `seeking_custodians` initialized to `false` to prevent unsolicited network traffic. Once your blind policy is configured, announce your availability to prospective workers:
```json
{
  "SetSeekingCustodians": {
    "ca_id_hex": "<CA_ID_HEX>",
    "seeking": true
  }
}
```
When set to `true`, prospective workers scanning the CA catalog know the node is accepting petitions. When set to `false`, incoming petitions are dropped immediately by the router.

### Step 3: Inspect Active Custodians (`ListCustodians`)
To audit active custodians, verify quota allocations, and review connected endpoints:
```json
{
  "ListCustodians": {
    "ca_id_hex": "<CA_ID_HEX>"
  }
}
```
Returns a list of active `CustodianSwarmRecord` entries containing `worker_pubkey`, `work_share_pct`, `tcp_endpoint`, `activated_at`, `contract_hash`, and `mock_cert_hash`.

### Step 4: Evicting Custodians (`RemoveCustodian`)
If a worker exhibits degraded performance, latency spikes, or downtime, revoke its membership:
```json
{
  "RemoveCustodian": {
    "ca_id_hex": "<CA_ID_HEX>",
    "worker_pubkey_hex": "<WORKER_PUBKEY_HEX>"
  }
}
```
The worker is atomically purged from `custodians.json`, freeing up capacity within the `target_swarm_size` pool for new applicants.

## Retrocompatibility Guarantees

- **Wire Protocol**:
  - Added gossip payload types 17, 18, 19, 20 (`CUSTODIAN_CONTRACT`, `CUSTODIAN_DELEGATION_REQ`, `CA_CAPABILITIES_PROOF`, `SWARM_ACTIVATION_CONFIRM`). Fully additive without breaking earlier gossip wire parsers.
  - TCP server runs on the same port alongside UDP without port conflicts or socket collisions.
- **Database & Catalog**:
  - `seeking_custodians` in `CaDeclaration` defaults to `false` on missing fields (`#[serde(default)]`), preserving existing CA records.
  - Subtables initialized transparently upon startup if not already present.
